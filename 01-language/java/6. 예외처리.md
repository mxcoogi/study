## 개요

프로그램 실행 중 문제가 생겼을 때 **프로그램이 비정상적으로 종료되지 않도록** 대비하는 방법을 정리한다.

| 주제 | 핵심 |
| --- | --- |
| 예외 계층 | Error vs Exception, Checked vs Unchecked |
| try-catch-finally | 예외를 잡아서 처리, 반드시 실행할 코드 |
| throw / throws | 예외를 직접 발생시키기, 호출한 쪽에 처리 떠넘기기 |
| try-with-resources | 자원을 자동으로 닫기 |
| 사용자 정의 · 되던지기 · 연결된 예외 | 예외를 설계하고 전달하는 방법 |

---

# 1. 프로그램 오류

프로그램이 실행 중 **오작동하거나 비정상적으로 종료**되는 원인을 **에러(error)** 또는 **오류**라고 한다.

## 발생 시점에 따른 분류

| 종류 | 발생 시점 | 예 |
| --- | --- | --- |
| **컴파일 에러** | 컴파일할 때 | 문법 오류, 타입 불일치, 선언하지 않은 변수 사용 |
| **런타임 에러** | 실행할 때 | 0으로 나누기, null 참조, 배열 범위 초과 |
| **논리적 에러** | 실행은 되지만 **의도와 다르게 동작** | 재고가 음수가 됨, 할인이 두 번 적용됨 |

- 컴파일러는 문법과 타입은 검사하지만 **실행 중 생길 문제까지 막아 주지는 못한다.**
- 그래서 런타임 에러에 미리 대비하는 코드가 필요하다 → **예외 처리**.

## 에러 vs 예외

자바는 실행 중 발생하는 오류를 두 가지로 나눈다.

| 구분 | 의미 | 예 | 대응 |
| --- | --- | --- | --- |
| **에러 (Error)** | 발생하면 **복구할 수 없는** 심각한 오류 | `OutOfMemoryError`(메모리 부족), `StackOverflowError`(호출 스택 넘침) | 코드로 수습 불가 |
| **예외 (Exception)** | 발생해도 **수습할 수 있는** 덜 심각한 오류 | 파일 없음, 잘못된 입력, null 참조 | **예외 처리**로 대비 |

> 여기서 "오버플로우"는 **스택 오버플로우**(`StackOverflowError`, 끝나지 않는 재귀 등)를 말한다. `int` 값이 범위를 넘는 정수 오버플로우는 에러 없이 값이 넘어갈 뿐이다. (→ [[3. 기초 문법]], [[2. JVM]])

### 예외 처리 (Exception Handling)

| 항목 | 내용 |
| --- | --- |
| 정의 | 프로그램 실행 시 발생할 수 있는 **예외에 대비한 코드를 작성**하는 것 |
| 목적 | 프로그램의 **비정상 종료를 막고**, 정상적인 실행 상태를 유지하는 것 |

- 처리되지 않은 예외는 JVM의 **기본 예외 처리기**(UncaughtExceptionHandler)가 받아서, 예외 내용을 화면에 출력하고 프로그램을 종료한다.

# 2. 예외 클래스의 계층 구조

자바는 오류도 **클래스**로 정의한다. 모든 예외·에러의 조상은 **Throwable** 이다.

![The Throwable class and its most significant subclasses](https://docs.oracle.com/javase/tutorial/figures/essential/exceptions-throwable.gif)

*Throwable 과 주요 자손 클래스 (출처: Oracle, The Java Tutorials, How to Throw Exceptions)*

```text
Object
 └── Throwable
      ├── Error                         복구 불가 (OutOfMemoryError, StackOverflowError ...)
      └── Exception
           ├── IOException              ┐
           ├── ClassNotFoundException   ├ Checked 예외: 예외 처리 필수
           ├── ...                      ┘
           └── RuntimeException         ┐
                ├── ArithmeticException  │
                ├── NullPointerException ├ Unchecked 예외: 예외 처리 선택
                ├── ClassCastException   │
                └── ...                  ┘
```

## Checked 예외 vs Unchecked 예외

| 구분 | Checked 예외 | Unchecked 예외 |
| --- | --- | --- |
| 해당 클래스 | Exception 과 그 자손 (**RuntimeException 제외**) | **RuntimeException** 과 그 자손 (+ Error) |
| 원인 | 주로 **외부 요인** (사용자 입력, 파일, 네트워크) | 주로 **프로그래머의 실수** |
| 컴파일러 검사 | **예외 처리를 강제**한다. 안 하면 **컴파일 에러** | 검사하지 않는다 |
| 예 | `IOException`, `FileNotFoundException`, `ClassNotFoundException`, `SQLException` | `ArithmeticException`, `NullPointerException`, `ArrayIndexOutOfBoundsException`, `ClassCastException`, `IllegalArgumentException`, `NumberFormatException` |

### 자주 만나는 RuntimeException

| 예외 | 언제 |
| --- | --- |
| `ArithmeticException` | 정수를 0으로 나눌 때 |
| `NullPointerException` | null 인 참조 변수로 멤버를 사용할 때 |
| `ArrayIndexOutOfBoundsException` | 배열의 범위를 벗어난 인덱스를 쓸 때 |
| `ClassCastException` | 형변환할 수 없는 타입으로 형변환할 때 (→ [[5. 객체지향 II]] 다형성) |
| `IllegalArgumentException` | 메서드에 잘못된 인자를 넘겼을 때 |
| `NumberFormatException` | `Integer.parseInt("abc")` 처럼 숫자로 바꿀 수 없을 때 |
| `IllegalStateException` | 객체의 상태가 메서드를 호출하기에 적절하지 않을 때 |

> RuntimeException 까지 처리를 강제하면 **모든 참조 변수 사용마다** try-catch 를 써야 한다. 그래서 컴파일러가 검사하지 않는다. 대신 **코드를 올바르게 작성해서 예방**한다 (null 체크, 범위 체크 등).

# 3. 예외 처리하기: try-catch

```java
try {
    // 예외가 발생할 가능성이 있는 문장
} catch (Exception1 e1) {
    // Exception1 이 발생했을 때 처리할 문장
} catch (Exception2 e2) {
    // Exception2 가 발생했을 때 처리할 문장
}
```

- 하나의 try 블럭 다음에는 **여러 개의 catch 블럭**이 올 수 있다.
- 발생한 예외와 **일치하는 catch 블럭 하나만** 실행된다.
- 일치하는 catch 블럭이 없으면 예외는 처리되지 않는다.
- try, catch 블럭은 문장이 하나여도 **괄호 `{ }` 를 생략할 수 없다.**
- catch 블럭의 참조 변수 이름은 블럭마다 **같아도 된다** (각 블럭 안에서만 유효). 단, 바깥 범위의 변수와 이름이 겹치면 안 된다.

```java
int number = 100;
int result = 0;

for (int i = 0; i < 10; i++) {
    try {
        result = number / (int) (Math.random() * 10);   // 0 으로 나눌 수도 있음
        System.out.println(result);
    } catch (ArithmeticException e) {
        System.out.println("0");                         // 예외가 나도 반복은 계속
    }
}
```

# 4. try-catch 문의 흐름

| 상황 | 흐름 |
| --- | --- |
| try 에서 **예외 발생 X** | try 블럭을 끝까지 실행 → catch 는 **건너뛰고** try-catch 다음 문장 |
| try 에서 **예외 발생 O**, 일치하는 catch **있음** | 예외 발생 위치 **이후의 try 문장은 실행하지 않음** → 일치하는 catch 실행 → try-catch 다음 문장 |
| try 에서 **예외 발생 O**, 일치하는 catch **없음** | 예외가 처리되지 않음 → 메서드 종료, 호출한 쪽으로 예외 전달 |

```java
System.out.println(1);
try {
    System.out.println(2);
    System.out.println(0 / 0);    // ArithmeticException 발생
    System.out.println(3);        // 실행되지 않음
} catch (ArithmeticException ae) {
    System.out.println(4);
}
System.out.println(5);

// 출력: 1 2 4 5
```

> 예외가 날 수 있는 문장과 **함께 실행되어야 하는 문장**만 try 에 넣는다. 예외와 상관없는 문장까지 넣으면, 예외 발생 시 그 문장들도 건너뛰게 된다.

# 5. 예외의 발생과 catch 블럭

## catch 블럭은 어떻게 고르나

1. 예외가 발생하면 그 예외 클래스의 **인스턴스가 만들어진다.** (`ArithmeticException` 이면 `new ArithmeticException()`)
2. 첫 번째 catch 블럭부터 차례로 `발생한예외 instanceof catch의타입` 을 검사한다.
3. 결과가 **true 인 첫 번째 catch 블럭**을 실행한다.

- `catch (Exception e)` 는 **모든 예외**를 잡는다. 모든 예외 클래스가 Exception 의 자손이기 때문이다.

## catch 블럭의 순서

자손 예외를 **먼저**, 조상 예외를 **나중에** 쓴다.

```java
try {
    ...
} catch (ArithmeticException e) {   // 구체적인 예외 먼저
    ...
} catch (Exception e) {             // 나머지 모든 예외
    ...
}
```

- 반대로 쓰면 아래 catch 는 절대 실행될 수 없어 **컴파일 에러**(unreachable)가 난다.

## printStackTrace() 와 getMessage()

예외 인스턴스에는 발생한 예외의 정보가 담겨 있다. catch 블럭의 참조 변수로 꺼내 쓴다.

| 메서드 | 내용 |
| --- | --- |
| `getMessage()` | 예외 인스턴스에 저장된 **메시지** |
| `printStackTrace()` | 예외 발생 당시의 **호출 스택**에 있던 메서드 정보와 메시지를 출력 |

```java
try {
    System.out.println(0 / 0);
} catch (ArithmeticException ae) {
    System.out.println(ae.getMessage());   // / by zero
    ae.printStackTrace();
    // java.lang.ArithmeticException: / by zero
    //     at ExceptionEx.main(ExceptionEx.java:4)
}
```

> 실무에서는 `printStackTrace()` 대신 **로거**를 쓴다: `log.error("계산 실패", e);`

## 멀티 catch 블럭 (Java 7+)

여러 catch 블럭을 `|` 로 **하나로 합칠** 수 있다.

```java
try {
    ...
} catch (ExceptionA | ExceptionB e) {
    e.printStackTrace();
}
```

- `|` 로 연결한 예외들이 **조상-자손 관계면 컴파일 에러**. (조상 하나만 쓰면 되므로 불필요한 코드)
- 참조 변수 e 로는 연결된 예외들의 **공통 조상의 멤버**만 쓸 수 있다.
- 참조 변수 e 는 **final** 이라 다른 값을 대입할 수 없다.

# 6. 예외 발생시키기: throw

`throw` 키워드로 예외를 **직접 발생**시킬 수 있다.

```java
Exception e = new Exception("고의로 발생시킴");   // 1. 예외 객체 생성
throw e;                                          // 2. 예외 발생

throw new Exception("고의로 발생시킴");            // 한 줄로
```

- 생성자에 넘긴 문자열은 예외의 **메시지**로 저장되고 `getMessage()` 로 꺼낼 수 있다.

## 컴파일러는 Checked 예외만 검사한다

```java
public static void main(String[] args) {
    throw new Exception();          // 컴파일 에러: 처리되지 않은 Checked 예외
}

public static void main(String[] args) {
    throw new RuntimeException();   // 컴파일 OK (실행하면 비정상 종료)
}
```

# 7. 메서드에 예외 선언하기: throws

메서드 선언부에 `throws` 로 **메서드 안에서 발생할 수 있는 예외**를 적는다. 예외를 직접 처리하지 않고 **호출한 메서드에게 처리를 넘긴다.**

```java
void method() throws Exception1, Exception2, ... ExceptionN {
    // 메서드 내용
}
```

- `throws Exception` 이라고 쓰면 **모든 종류의 예외**가 발생할 수 있다는 뜻이다.
- 보통 **Checked 예외만** 선언한다. RuntimeException 은 적지 않는 것이 관례이다.
- 메서드 선언부만 보고도 **어떤 예외를 처리해야 하는지** 알 수 있다 (API 문서의 Throws 항목).
- 오버라이딩할 때는 조상 메서드보다 **많은(넓은) 예외를 선언할 수 없다.** (→ [[5. 객체지향 II]])

## 예외는 호출 스택을 따라 전달된다

```java
public static void main(String[] args) throws Exception {
    method1();
}
static void method1() throws Exception {
    method2();
}
static void method2() throws Exception {
    throw new Exception();
}
```

```text
java.lang.Exception
    at ExceptionEx.method2(ExceptionEx.java:9)    ← 예외가 발생한 곳
    at ExceptionEx.method1(ExceptionEx.java:6)
    at ExceptionEx.main(ExceptionEx.java:3)       ← 맨 아래: 처음 호출된 메서드
```

1. method2 에서 예외 발생 → 처리하지 않고 method2 종료, method1 으로 넘어감
2. method1 도 처리하지 않음 → main 으로 넘어감
3. main 도 처리하지 않음 → **JVM 기본 예외 처리기**가 받아 위 내용을 출력하고 프로그램 종료

![Searching the call stack for the exception handler](https://docs.oracle.com/javase/tutorial/figures/essential/exceptions-errorOccurs.gif)

*예외 처리기를 찾는 과정: 예외가 발생한 메서드부터 호출 스택을 거꾸로 내려가며 예외를 처리할 수 있는 메서드를 찾는다 (출처: Oracle, The Java Tutorials, What Is an Exception?)*

> `throws` 는 예외를 **처리하는 것이 아니라 떠넘기는 것**이다. 결국 어딘가에서는 try-catch 로 처리해야 한다.

## 어디서 처리할까

| 방식 | 언제 |
| --- | --- |
| **메서드 안에서 처리** (try-catch) | 그 메서드 안에서 **해결할 수 있을 때** (기본값으로 대체, 재시도 등) |
| **호출한 쪽에 떠넘기기** (throws) | 호출한 쪽이 **상황을 알고 결정해야 할 때** (잘못된 파일 이름 → 사용자에게 다시 입력받기) |

# 8. finally 블럭

예외 발생 여부와 관계없이 **반드시 실행되어야 할 코드**를 넣는다. try-catch 의 맨 끝에 둔다.

```java
try {
    // 예외가 발생할 가능성이 있는 문장
} catch (Exception e) {
    // 예외 처리
} finally {
    // 예외 발생 여부와 관계없이 항상 실행 (자원 정리 등)
}
```

| 상황 | 실행 순서 |
| --- | --- |
| 예외 발생 O | try → **catch** → finally |
| 예외 발생 X | try → finally |

```java
try {
    startInstall();
    copyFiles();
} catch (Exception e) {
    e.printStackTrace();
} finally {
    deleteTempFiles();   // 성공하든 실패하든 임시 파일 삭제
}
```

## return 이 있어도 finally 는 실행된다

```java
static void method() {
    try {
        System.out.println("try");
        return;                         // 메서드를 끝내기 전에
    } catch (Exception e) {
        System.out.println("catch");
    } finally {
        System.out.println("finally");  // finally 가 먼저 실행된다
    }
}
// 출력: try, finally
```

- 예외: `System.exit()` 로 JVM 을 종료하면 finally 도 실행되지 않는다.
- finally 블럭 안에서 `return` 하지 않는다. try 의 반환값이나 예외를 **덮어써서** 버그를 숨긴다.

# 9. 자동 자원 반환: try-with-resources (Java 7+)

파일, 네트워크 연결, DB 커넥션처럼 **사용 후 반드시 닫아야 하는 자원**을 자동으로 닫아 준다.

## 기존 방식의 문제

```java
FileInputStream fis = null;
DataInputStream dis = null;
try {
    fis = new FileInputStream("score.dat");
    dis = new DataInputStream(fis);
    ...
} catch (IOException e) {
    e.printStackTrace();
} finally {
    try {
        if (dis != null) dis.close();    // close() 도 예외를 던질 수 있어서
    } catch (IOException e) {            // finally 안에 또 try-catch
        e.printStackTrace();
    }
}
```

- 코드가 복잡하고, try 와 close() 에서 **둘 다 예외가 나면 try 쪽 예외가 사라진다.**

## try-with-resources

```java
try (FileInputStream fis = new FileInputStream("score.dat");
     DataInputStream dis = new DataInputStream(fis)) {   // 괄호 안에서 자원 생성

    while (true) {
        score = dis.readInt();
        ...
    }
} catch (EOFException e) {

} catch (IOException e) {
    e.printStackTrace();
}
// try 블럭을 벗어나면 dis, fis 의 close() 가 자동 호출된다
```

| 규칙 | 설명 |
| --- | --- |
| 대상 | **`AutoCloseable` 인터페이스를 구현한 클래스**만 쓸 수 있다 |
| 닫는 시점 | try 블럭을 벗어날 때 (정상 종료든 예외든) |
| 닫는 순서 | 선언한 **역순**으로 닫는다 (dis → fis) |
| 여러 자원 | 괄호 안에서 `;` 로 구분 |
| Java 9+ | 바깥에서 만든 **effectively final** 변수도 쓸 수 있다: `try (resource) { ... }` |

```java
public interface AutoCloseable {
    void close() throws Exception;
}
```

## 억제된 예외 (Suppressed Exception)

- try 블럭과 `close()` 에서 **둘 다 예외**가 나면, try 의 예외가 **실제로 던져지고**, close() 의 예외는 **억제된 예외**로 붙는다.
- 두 예외를 모두 잃지 않는다.

```java
try (CloseableResource cr = new CloseableResource()) {
    cr.exceptionWork(true);              // 예외 발생
} catch (Exception e) {
    e.printStackTrace();
    // WorkException: ...
    //     Suppressed: CloseException: ...   ← close() 에서 난 예외
}

Throwable[] suppressed = e.getSuppressed();   // 억제된 예외 꺼내기
```

# 10. 사용자 정의 예외 만들기

기존 예외 클래스를 **상속**해서 필요한 예외를 직접 만든다.

```java
class MyException extends Exception {
    private final int errorCode;              // 추가 정보: 에러 코드

    MyException(String msg) {
        this(msg, 100);
    }

    MyException(String msg, int errorCode) {
        super(msg);                           // 조상(Exception)의 생성자로 메시지 저장
        this.errorCode = errorCode;
    }

    public int getErrorCode() { return errorCode; }
}
```

| 조상 선택 | 결과 |
| --- | --- |
| `extends Exception` | Checked 예외: 호출한 쪽이 **반드시 처리**해야 한다 |
| `extends RuntimeException` | Unchecked 예외: 처리를 **선택**할 수 있다 |

- 요즘은 **RuntimeException 을 상속**하는 경우가 많다. Checked 예외는 처리할 수 없는 상황에서도 try-catch 나 throws 를 강제해 코드가 지저분해지기 때문이다.
- 이름은 `~Exception` 으로 끝내고, 무엇이 잘못됐는지 드러나게 짓는다. (`InsufficientStockException`, `MemberNotFoundException`)

```java
class SpaceException  extends Exception { SpaceException(String msg)  { super(msg); } }
class MemoryException extends Exception { MemoryException(String msg) { super(msg); } }

static void install() throws SpaceException, MemoryException {
    if (!enoughSpace())  throw new SpaceException("설치할 공간이 부족합니다.");
    if (!enoughMemory()) throw new MemoryException("메모리가 부족합니다.");
}

try {
    install();
} catch (SpaceException e) {
    System.out.println("에러 메시지 : " + e.getMessage());
    System.out.println("공간을 확보한 후에 다시 설치하시기 바랍니다.");
} catch (MemoryException e) {
    System.out.println("에러 메시지 : " + e.getMessage());
    System.gc();
    System.out.println("다시 설치를 시도하세요.");
}
```

# 11. 예외 되던지기 (Exception Re-throwing)

예외를 catch 로 **일부 처리한 뒤, 다시 throw** 해서 호출한 쪽에서도 처리하게 하는 것이다.

```java
static void method1() throws Exception {   // 되던지므로 throws 선언 필요 (Checked 예외인 경우)
    try {
        throw new Exception();
    } catch (Exception e) {
        System.out.println("method1 에서 처리");   // 1. 여기서 일부 처리
        throw e;                                    // 2. 다시 발생시킴
    }
}

public static void main(String[] args) {
    try {
        method1();
    } catch (Exception e) {
        System.out.println("main 에서 처리");      // 3. 호출한 쪽에서도 처리
    }
}
// 출력: method1 에서 처리, main 에서 처리
```

- 하나의 예외를 **양쪽에서 나눠 처리**해야 할 때 쓴다. (예: 로그는 여기서 남기고, 사용자 안내는 호출한 쪽에서)
- 메서드에 return 값이 있으면 catch 블럭에도 return 이 필요하지만, **throw 로 되던지면 return 이 없어도 된다.**

# 12. 연결된 예외 (Chained Exception)

한 예외가 **다른 예외를 원인(cause)으로** 가지게 하는 것이다.

```java
try {
    startInstall();
} catch (SpaceException e) {
    InstallException ie = new InstallException("설치 중 예외 발생");
    ie.initCause(e);       // InstallException 의 원인으로 SpaceException 지정
    throw ie;
}

// 생성자로 원인을 넘기는 것이 더 일반적
throw new InstallException("설치 중 예외 발생", e);
```

| 메서드 | 의미 |
| --- | --- |
| `Throwable initCause(Throwable cause)` | 원인 예외를 등록 |
| `Throwable getCause()` | 원인 예외를 반환 |
| 생성자 `Exception(String msg, Throwable cause)` | 메시지와 원인을 함께 지정 |

## 왜 쓰나

### 1. 여러 예외를 하나로 묶기

```java
// 세부 예외를 하나하나 throws 에 쓰지 않고
void install() throws SpaceException, MemoryException { ... }

// 큰 분류의 예외 하나로 묶고, 원인은 cause 에 담는다
void install() throws InstallException { ... }
```

- 예외들을 공통 조상으로 묶으면 **실제로 어떤 예외였는지** 알 수 없다. 연결된 예외로 감싸면 원인을 잃지 않는다.

### 2. Checked 예외를 Unchecked 예외로 바꾸기

```java
static void startInstall() {
    if (!enoughSpace())
        throw new RuntimeException(new SpaceException("설치할 공간이 부족합니다."));
}
```

- 호출한 쪽에서 처리할 수 없는 Checked 예외를 **RuntimeException 으로 감싸서** 불필요한 throws 를 없앤다.
- printStackTrace() 를 하면 `Caused by: SpaceException ...` 으로 원인까지 출력된다.

---

# 실무에서 주의할 것

- **예외를 삼키지 않는다.** 빈 catch 블럭(`catch (Exception e) { }`)은 문제가 생겨도 아무도 모르게 만든다. 최소한 로그라도 남긴다.
- **`catch (Exception e)` 로 다 잡지 않는다.** 처리할 수 있는 구체적인 예외만 잡는다.
- 예외를 감쌀 때는 **원인(cause)을 꼭 넘긴다.** `new RuntimeException(e)` 처럼. 원인을 빼면 진짜 원인을 추적할 수 없다.
- **스프링 `@Transactional`** 은 기본적으로 **RuntimeException(Unchecked)과 Error 에서만 롤백**하고, Checked 예외에서는 **커밋**한다. Checked 예외에서도 롤백하려면 `@Transactional(rollbackFor = Exception.class)`.

---

# 핵심 정리

- 오류: 컴파일 / 런타임 / 논리적. 런타임 오류 중 **Error** 는 복구 불가, **Exception** 은 처리 가능.
- 모든 예외의 조상은 **Throwable**. **RuntimeException 과 자손 = Unchecked**, 나머지 Exception = **Checked**(처리 강제).
- try 에서 예외가 나면 이후 문장은 건너뛰고, `instanceof` 가 true 인 **첫 catch** 만 실행. 자손 예외 catch 를 **먼저**.
- 멀티 catch 의 예외들은 조상-자손 관계 X.
- `throw` = 예외 발생, `throws` = 호출한 쪽으로 떠넘기기. 끝까지 처리 안 하면 JVM 이 스택 트레이스 출력 후 종료.
- `finally` 는 return 이 있어도 실행 (`System.exit()` 제외).
- try-with-resources: `AutoCloseable` 자원을 **역순**으로 자동 close, close 예외는 **suppressed** 로 보존.
- 사용자 정의 예외는 요즘 **RuntimeException** 상속이 일반적.
- 되던지기 = 일부 처리 후 다시 throw. 연결된 예외 = `cause` 로 원인 보존, Checked → Unchecked 변환.
