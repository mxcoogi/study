## 개요

**JVM(Java Virtual Machine)**은 자바 바이트코드(`.class`)를 실행하는 **가상 컴퓨터**이다.

자바 프로그램이 실행되면 JVM은 운영체제로부터 프로그램 수행에 필요한 **메모리를 할당**받고, 이 메모리를 **용도에 따라 여러 영역으로 나눠** 관리한다.

> 플랫폼 독립성(WORA)은 → [[01. 자바란?]]

## JDK · JRE · JVM

```text
┌─────────────────────────────────────────┐
│ JDK  (Java Development Kit)             │  개발 도구: javac, jar, javadoc, jdb ...
│  ┌───────────────────────────────────┐  │
│  │ JRE  (Java Runtime Environment)   │  │  실행 환경: 표준 라이브러리 (java.lang, java.util ...)
│  │  ┌─────────────────────────────┐  │  │
│  │  │ JVM                         │  │  │  바이트코드 실행
│  │  └─────────────────────────────┘  │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

| 구분 | 용도 |
| --- | --- |
| **JDK** | 자바 프로그램을 **개발**할 때 (컴파일러 포함) |
| **JRE** | 자바 프로그램을 **실행만** 할 때 |
| **JVM** | 바이트코드를 실제로 실행하는 엔진 |

> Java 11부터 JRE를 따로 배포하지 않는다. 개발이든 실행이든 JDK를 설치한다.

```text

    ▼
Hello.class  (바이트코드)

│          │                                             │

    │
    ▼

```

## 1. 클래스 로더 (Class Loader)

프로그램 실행 중 **어떤 클래스가 필요해지는 순간** `.class` 파일을 읽어 JVM 메모리에 올린다. 처음에 모든 클래스를 올리지 않고 **필요할 때 올린다 (동적 로딩)**.

### 로딩 단계

| 단계 | 하는 일 |
| --- | --- |
| **Loading** | `.class` 파일을 읽어 Method Area 에 클래스 정보 저장 |
| **Linking** | **Verify**: 바이트코드가 올바른지 검사 / **Prepare**: 클래스 변수(static) 메모리 할당 후 **기본값**으로 초기화 / **Resolve**: 심볼릭 참조를 실제 주소로 바꿈 |
| **Initialization** | 클래스 변수에 **지정한 초기값** 대입, `static {}` 블록 실행 |

### 클래스 로더 계층과 부모 위임

```text
Bootstrap ClassLoader     java.lang.* 등 핵심 클래스 (JDK 내부)
        ▲
Platform ClassLoader      java.sql 등 JDK 확장 모듈
        ▲
Application ClassLoader   내가 만든 클래스, classpath 의 라이브러리
```

- 클래스를 찾을 때 **부모에게 먼저 위임**하고, 부모가 못 찾으면 자신이 찾는다.
- 덕분에 내가 `java.lang.String` 을 만들어도 진짜 `String` 이 덮어써지지 않는다 (보안).

## 2. 런타임 데이터 영역 (Runtime Data Area)

JVM이 프로그램 실행을 위해 운영체제에서 할당받은 메모리 영역이다.

```text
┌──────────────── 모든 스레드가 공유 ────────────────┐ ┌──────── 스레드마다 하나씩 ─────────┐
│                                                  │ │                                 │
│  Method Area            Heap                     │ │  Call Stack    PC      Native   │
│  ┌──────────────┐      ┌──────────────────────┐  │ │  ┌─────────┐  Register Method   │
│  │ 클래스 정보     │      │ 인스턴스 (new 로 생성)   │  │ │  │ 프레임    │           Stack    │
│  │ 클래스 변수     │      │ 인스턴스 변수           │  │ │  │ 지역 변수  │                    │
│  │ 상수 풀        │      │ 배열                  │  │ │  └─────────┘                    │
│  └──────────────┘      └──────────────────────┘  │ │                                 │
└──────────────────────────────────────────────────┘ └─────────────────────────────────┘
```

| 영역 | 저장하는 것 | 생성 단위 |
| --- | --- | --- |
| **Method Area** | 클래스 정보, **클래스 변수**, 메서드 코드, 상수 풀 | JVM 하나 (공유) |
| **Heap** | **인스턴스**, **인스턴스 변수**, 배열 | JVM 하나 (공유) |
| **Call Stack** | 메서드 작업 공간 (**지역 변수**, 매개변수, 연산 중간값) | **스레드마다** |
| **PC Register** | 현재 실행 중인 명령어 주소 | 스레드마다 |
| **Native Method Stack** | C/C++ 로 작성된 네이티브 메서드용 스택 | 스레드마다 |

> **공유 영역**(Method Area, Heap)은 여러 스레드가 동시에 접근하므로 **동시성 문제**가 생길 수 있다. 지역 변수는 스레드마다 따로라 안전하다. (→ 쓰레드에서 다시)

---

### 메서드 영역 (Method Area)

- 프로그램 실행 중 어떤 클래스가 필요하면 JVM은 해당 클래스의 **클래스 파일을 읽고 분석**해서 클래스 정보를 이곳에 저장한다.
- 이때 그 클래스의 **클래스 변수(static 변수)**도 함께 저장된다.
- 클래스 이름, 메서드 코드, 필드 정보, **런타임 상수 풀**(리터럴, 심볼릭 참조) 등을 저장한다.

> **실제 구현 (HotSpot JVM, Java 8+)**
> - Method Area 는 **Metaspace** 라는 이름으로 JVM 힙이 아닌 **네이티브 메모리**에 있다. (Java 7까지는 PermGen)
> - static 변수의 실제 값과 문자열 상수 풀(String Pool)은 **Heap** 에 저장된다.
> - 책에서 "클래스 변수는 Method Area" 라고 하는 것은 **개념(JVM 명세) 기준**이다.

---

### 힙 (Heap)

- **인스턴스가 생성되는 공간**. 프로그램 실행 중 `new` 로 만든 인스턴스와 배열은 **모두** 이곳에 생성된다.
- 즉 **인스턴스 변수**가 생성되는 공간이다.
- 더 이상 참조되지 않는 인스턴스는 **GC**가 정리한다.

```java
void method() {
    Tv t = new Tv();   // t 는 지역 변수 → Call Stack
                       // new Tv() 인스턴스 → Heap
}
```

```text
Call Stack                      Heap
┌──────────────┐               ┌───────────────────┐
│ method()     │               │ Tv 인스턴스          │
│  t = 0x100 ──┼──────────────▶│  color, power,    │
└──────────────┘               │  channel          │
                               └───────────────────┘
```

#### 힙의 세대 구조 (Generational Heap)

```text
┌──────────────── Young Generation ────────────────┬────── Old Generation ──────┐
│  Eden            Survivor 0    Survivor 1        │                            │
│  (새 객체 생성)    (살아남은 객체가 옮겨 다님)          │  오래 살아남은 객체           │
└──────────────────────────────────────────────────┴────────────────────────────┘
```

- 대부분의 객체는 **금방 쓸모없어진다** (Weak Generational Hypothesis). 그래서 새 객체 영역(Young)과 오래된 객체 영역(Old)을 나눠 관리한다.
- 새 객체는 **Eden** 에 생성 → GC 에서 살아남으면 Survivor 로 → 여러 번 살아남으면 **Old** 로 이동(Promotion).

![Default Arrangement of Generations](https://docs.oracle.com/en/java/javase/21/gctuning/img/jsgct-dt-001-armgnt-gn-new1.png)

*Figure 3-2 Default Arrangement of Generations in the Serial Collector (출처: Oracle, HotSpot GC Tuning Guide, Java 21)*

- **Young** = Eden + Survivor 2개, 나머지는 **Old**.
- **Virtual**: 예약만 해 두고 아직 실제로 쓰지 않는 공간. 힙이 커져야 할 때 이 공간까지 늘어난다 (`-Xms` 에서 `-Xmx` 까지).

#### 왜 세대를 나누나

![Typical Distribution for Lifetimes of Objects](https://docs.oracle.com/en/java/javase/21/gctuning/img/jsgct-dt-003-alc-vs-srvng2.png)

*Figure 3-1 Typical Distribution for Lifetimes of Objects (출처: Oracle, HotSpot GC Tuning Guide, Java 21)*

- 가로축은 할당된 바이트(시간 흐름), 세로축은 살아남은 바이트.
- 왼쪽 끝의 뾰족한 봉우리: 새로 만든 객체 대부분이 **금방 죽는다** → Young 만 자주 청소하는 **Minor GC** 로 대부분 회수된다.
- 오래 살아남은 소수만 Old 로 가서 드물게 **Major GC** 로 정리된다.

### 호출 스택 (Call Stack)

- 호출 스택은 **메서드의 작업에 필요한 메모리 공간**을 제공한다.
- 메서드가 호출되면 호출 스택에 그 메서드를 위한 작업 공간(**스택 프레임**)이 할당된다.
- 이 공간은 메서드가 작업하는 동안 **지역 변수(매개변수 포함)**와 **연산의 중간 결과**를 저장하는 데 쓰인다.
- 작업 공간은 **메서드마다 구별**된다.
- 메서드가 종료되면 할당된 공간은 **자동으로 반환**된다.

#### 동작 방식

- 첫 메서드가 호출되면 스택 **맨 아래**에 그 메서드의 공간이 생긴다.
- 그 메서드가 다른 메서드를 호출하면, **바로 위에** 호출된 메서드의 공간이 생긴다.
- 호출한 메서드는 **수행을 멈추고 기다린다.** 호출된 메서드가 끝나면 다시 이어서 수행한다.

#### 호출 스택의 특징

- 메서드가 호출되면 수행에 필요한 메모리를 스택에 **할당**받는다.
- 메서드가 수행을 마치면 할당받은 메모리가 스택에서 **자동으로 제거**된다.
- 호출 스택의 **제일 위**에 있는 메서드가 **현재 실행 중**인 메서드이고, 나머지는 대기 상태다.
- 아래에 있는 메서드가 **바로 위의 메서드를 호출한** 메서드다.

#### 예제: 호출 스택의 변화

```java
class CallStack {
    public static void main(String[] args) {
        firstMethod();
    }

    static void firstMethod() {
        secondMethod();
    }

    static void secondMethod() {
        System.out.println("secondMethod()");
    }
}
```

```text
 ①            ②            ③              ④              ⑤             ⑥            ⑦
                                       ┌──────────┐
                         ┌──────────┐  │ println  │  ┌──────────┐
            ┌──────────┐ │ second   │  │ second   │  │ second   │  ┌──────────┐
┌────────┐  │ first    │ │ first    │  │ first    │  │ first    │  │ first    │ ┌──────────┐
│ main   │  │ main     │ │ main     │  │ main     │  │ main     │  │ main     │ │ main     │   (비어 있음)
└────────┘  └──────────┘ └──────────┘  └──────────┘  └──────────┘  └──────────┘ └──────────┘

① main 호출   ② first 호출   ③ second 호출   ④ println 호출   ⑤ println 종료
⑥ second 종료   ⑦ first 종료   → main 이 끝나면 스택이 비고 프로그램 종료
```

#### 스택 프레임의 구성

| 구성 | 저장하는 것 |
| --- | --- |
| **지역 변수 배열** | 매개변수, 지역 변수 (인스턴스 메서드면 0번에 `this`) |
| **피연산자 스택** | 연산 중간 결과 (`a + b` 를 계산할 때 a, b 를 올려 두는 곳) |
| **프레임 데이터** | 반환 주소, 상수 풀 참조 등 |

---

### PC Register · Native Method Stack

- **PC Register**: 스레드가 **지금 실행 중인 바이트코드 명령의 주소**를 저장한다. 스레드가 번갈아 실행될 때 어디까지 했는지 기억하는 용도.
- **Native Method Stack**: 자바가 아닌 C/C++ 코드(네이티브 메서드, JNI)를 실행할 때 쓰는 스택.

## 3. 실행 엔진 (Execution Engine)

| 구성 | 동작 |
| --- | --- |
| **Interpreter** | 바이트코드를 **한 줄씩** 해석해서 실행. 시작은 빠르지만 반복 실행에 느림 |
| **JIT Compiler** | 자주 실행되는 코드(**hot spot**)를 찾아 **기계어로 통째로 컴파일**하고 캐시. 이후에는 기계어를 바로 실행해 빠름 |
| **GC** | Heap 에서 더 이상 쓰지 않는 객체를 찾아 메모리를 회수 |

> 자바 프로그램이 처음에는 느리다가 점점 빨라지는 이유 = JIT 컴파일 (워밍업)

## 가비지 컬렉션 (GC)

### GC 대상

- **어디에서도 참조되지 않는 객체(unreachable)**가 대상이다.
- 출발점(**GC Root**): 스택의 지역 변수, static 변수, JNI 참조 등. 여기서 따라갈 수 없는 객체는 쓰레기로 본다.

```java
Tv t = new Tv();   // 인스턴스 A
t = new Tv();      // 인스턴스 B 를 가리킴 → A 는 아무도 참조하지 않음 → GC 대상
t = null;          // B 도 GC 대상
```

### GC 동작 (Mark and Sweep)

```text
Mark     GC Root 에서 출발해 참조를 따라가며 살아 있는 객체에 표시
Sweep    표시 안 된 객체의 메모리를 회수
Compact  (선택) 살아 있는 객체를 한쪽으로 모아 메모리 조각을 없앰
```

### 세대별 GC 과정 (Minor GC)

1. 새 객체는 모두 **Eden** 에 생성된다. Survivor 두 곳은 비어 있다.
2. Eden 이 꽉 차면 **Minor GC** 가 발생한다.
3. 살아남은 객체는 **Survivor 0** 으로 이동하고 나이(age)가 1 증가한다. 나머지는 삭제되고 Eden 은 비워진다.
4. 다음 Minor GC 에서는 Eden 과 Survivor 0 의 생존 객체를 **Survivor 1** 로 옮긴다. 두 Survivor 는 번갈아 쓰이고 **하나는 항상 비어 있다.**
5. 나이가 기준값(예: 8)에 도달한 객체는 **Old Generation 으로 승격(Promotion)** 된다.
6. 결국 Old 가 차면 **Major GC** 가 Old 를 정리하고 압축한다.

> Mark · Sweep · Compact 와 위 6단계를 그림으로 보기 → [Oracle 튜토리얼: Java Garbage Collection Basics](https://www.oracle.com/webfolder/technetwork/tutorials/obe/java/gc01/index.html) ("Describing Garbage Collection", "The Generational Garbage Collection Process" 부분. Java 7 기준이라 PermGen 이 나온다)

### Minor GC vs Major(Full) GC

| 구분 | 대상 | 특징 |
| --- | --- | --- |
| **Minor GC** | Young Generation | 자주 발생, 빠름 |
| **Major / Full GC** | Old Generation (Full 은 전체) | 드물게 발생, **오래 걸림** |

- **Stop-The-World**: GC 가 실행되는 동안 애플리케이션 스레드가 **멈춘다.** GC 튜닝은 대부분 이 멈춤 시간을 줄이는 것이다.

### 주요 GC 종류

| GC | 특징 |
| --- | --- |
| Serial GC | 스레드 하나로 GC. 작은 프로그램용 |
| Parallel GC | 여러 스레드로 GC. 처리량 중심 (Java 8 기본) |
| **G1 GC** | 힙을 작은 영역(Region)으로 나눠 관리. 멈춤 시간 예측 가능 (**Java 9+ 기본**) |
| **ZGC** | 멈춤 시간이 매우 짧음 (ms 이하). 큰 힙에 유리. Java 21에서 세대 구분(Generational ZGC) 지원 |

#### G1 GC 의 힙 구조

![G1 Garbage Collector Heap Layout](https://docs.oracle.com/en/java/javase/21/gctuning/img/jsgct-dt-004-grbg-frst-hp2.png)

*Figure 7-1 G1 Garbage Collector Heap Layout (출처: Oracle, HotSpot GC Tuning Guide, Java 21)*

- 힙을 Eden · Survivor · Old 로 **연속해서 나누지 않고**, 같은 크기의 **Region** 여러 개로 나눈다.
- 회색 = 빈 Region / 빨강 = Eden / 빨강 + **S** = Survivor / 하늘색 = Old / 하늘색 + **H** = Humongous (Region 하나보다 큰 객체, 여러 Region 을 이어서 사용)
- 쓰레기가 가장 많은 Region 부터 청소한다 → 이름이 **Garbage-First**.

| 에러 | 원인 | 예 |
| --- | --- | --- |
| **StackOverflowError** | Call Stack 공간 부족 | 종료 조건 없는 **재귀 호출** |
| **OutOfMemoryError: Java heap space** | Heap 공간 부족 | 객체를 계속 만들고 참조를 놓지 않음 (메모리 누수) |
| **OutOfMemoryError: Metaspace** | 클래스 메타데이터 공간 부족 | 클래스를 동적으로 너무 많이 생성 |

## 핵심 정리

- 실행 과정: `.java` → **javac** → `.class` → **Class Loader** → **Runtime Data Area** → **Execution Engine** → OS
- **Method Area**: 클래스 정보 + 클래스 변수 / **Heap**: 인스턴스 + 인스턴스 변수 / **Call Stack**: 지역 변수
- Method Area, Heap 은 **모든 스레드가 공유**, Call Stack 은 **스레드마다 따로**.
- 호출 스택: 맨 위가 실행 중, 메서드가 끝나면 자동 제거, 아래가 위를 호출한 메서드.
- Interpreter 로 시작 → 자주 쓰는 코드는 **JIT** 가 기계어로 컴파일.
- GC 는 **참조되지 않는 객체**를 회수. Young(Minor GC) / Old(Major GC), 실행 중 **Stop-The-World**.
- 무한 재귀 → **StackOverflowError**, 힙 부족 → **OutOfMemoryError**.

> 변수 종류와 메모리 위치 예제는 → [[04. 객체지향 I]]
