## 개요

**데이터 모델링**은 현실 세계의 업무를 데이터베이스로 옮기기 위해 **추상화·단순화·명확화**하여 표현하는 과정이다.

복잡한 현실을 그대로 저장할 수 없기 때문에, 업무에 필요한 데이터만 골라 구조를 정의하고 이를 **ERD** 같은 표기법으로 그려 설계자·개발자·현업이 같은 그림을 보고 이야기할 수 있게 만든다.

---

## 모델링의 특징

| 특징 | 설명 |
| --- | --- |
| **추상화** | 현실 세계를 일정한 형식에 맞추어 표현한다 (공통 성질만 뽑아냄) |
| **단순화** | 약속된 규약과 제한된 표기법으로 쉽게 이해할 수 있게 표현한다 |
| **명확화** | 애매모호함을 제거하고 정확하게 현상을 기술한다 |

---

## 모델링의 3가지 관점

| 관점 | 질문 | 내용 |
| --- | --- | --- |
| **데이터 관점** | What | 업무가 어떤 데이터와 관련 있는지, 데이터 간 관계는 무엇인지 |
| **프로세스 관점** | How | 업무가 실제로 하고 있는 일은 무엇인지, 무엇을 해야 하는지 |
| **상관 관점** | Interaction | 업무 처리 방법에 따라 데이터가 어떤 영향을 받는지 |

---

## 데이터 모델링의 3요소

| 요소 | 개념 (타입) | 개별 (인스턴스) |
| --- | --- | --- |
| 업무가 관여하는 **어떤 것 (Things)** | 엔터티 타입 / 엔터티 | 엔터티 / 인스턴스 / 어커런스 |
| 어떤 것이 가지는 **성격 (Attributes)** | 속성 | 속성값 |
| 어떤 것 간의 **관계 (Relationships)** | 관계 | 페어링 |

```text
엔터티  : 사원
인스턴스 : (1001, 김철수, 개발팀), (1002, 이영희, 인사팀) ...
속성    : 사번, 이름, 부서
속성값  : 1001, 김철수, 개발팀
```

---

## 모델링 시 유의점

- **중복 (Duplication)**: 같은 데이터가 여러 장소에 저장되지 않도록 한다.
- **비유연성 (Inflexibility)**: 사소한 업무 변화에도 모델이 수시로 바뀌지 않도록 데이터 정의와 프로세스를 분리한다.
- **비일관성 (Inconsistency)**: 데이터 간 상호 연관 관계를 명확히 정의해 한쪽만 수정되어 모순이 생기지 않게 한다.

---

## 데이터 모델링의 단계

```text
개념적 모델링  →  논리적 모델링  →  물리적 모델링
(추상화 높음)                       (추상화 낮음, 구체적)
```

| 단계 | 내용 |
| --- | --- |
| **개념적** | 추상화 수준이 가장 높고 업무 중심적·포괄적. 핵심 엔터티와 관계 도출, 전사적 데이터 모델(EA) 수립 시 사용 |
| **논리적** | 시스템 구축을 위한 Key, 속성, 관계를 정확히 표현. **정규화** 수행, 재사용성이 높음 |
| **물리적** | 실제 DB에 구현할 수 있도록 테이블, 인덱스, 저장 구조, 성능 등을 고려해 설계 |

---

## 3단계 스키마 구조 (ANSI-SPARC)

데이터 독립성을 확보하기 위해 DB를 바라보는 관점을 세 단계로 나눈다.

```text
  외부 스키마   (사용자/응용 프로그램 관점, 여러 개)
       │   ← 논리적 독립성
  개념 스키마   (통합 관점, DB 전체 구조, 1개)
       │   ← 물리적 독립성
  내부 스키마   (물리적 저장 구조, 1개)
```

| 스키마 | 설명 |
| --- | --- |
| **외부 스키마** | 사용자나 응용 프로그램이 보는 개인적 관점의 DB 구조 (View) |
| **개념 스키마** | 모든 사용자 관점을 통합한 **전체 DB**의 논리적 구조. 데이터와 관계, 제약조건 정의 |
| **내부 스키마** | 데이터가 디스크에 실제로 저장되는 방식 (파일 구조, 인덱스 등) |

- **논리적 독립성**: 개념 스키마가 바뀌어도 외부 스키마(응용 프로그램)는 영향받지 않는다.
- **물리적 독립성**: 내부 스키마(저장 구조)가 바뀌어도 개념 스키마는 영향받지 않는다.

## ERD (Entity Relationship Diagram)

- 1976년 **피터 첸(Peter Chen)**이 제안
- 대표 표기법: **Chen**, **IE(Information Engineering, 까마귀발)**, **Barker**

### ERD 작성 순서

```text
1. 엔터티를 그린다
2. 엔터티를 적절하게 배치한다
3. 엔터티 간 관계를 설정한다
4. 관계명을 기술한다
5. 관계의 참여도(관계 차수)를 기술한다
6. 관계의 필수 여부(선택성)를 기술한다
```

### 엔터티 배치

- 업무의 중심이 되는 엔터티를 **왼쪽 상단**에 둔다.
- 업무 흐름에 따라 중심 엔터티와 관련된 엔터티를 오른쪽·아래로 배치한다.

## 좋은 데이터 모델의 요소

- **완전성**: 업무에 필요한 데이터가 모두 정의되어 있다.
- **중복 배제**: 하나의 DB 내에 동일한 사실은 한 번만 기록한다.
- **업무 규칙**: 업무 규칙이 모델에 표현되어 있다.
- **데이터 재사용**: 통합성과 독립성을 고려해 재사용 가능하게 설계한다.
- **의사소통**: 모델을 보고 업무를 이해할 수 있다.
- **통합성**: 같은 데이터는 조직 전체에서 한 번만 정의되고 여러 곳에서 참조한다.

---

## 시험 포인트

- 모델링 특징 = **추상화, 단순화, 명확화** (복잡화·구체화 X)
- 관점: 데이터(What) / 프로세스(How) / 상관(Interaction)
- 유의점: **중복, 비유연성, 비일관성**
- 정규화는 **논리적** 모델링 단계, 성능·저장 고려는 **물리적** 단계
- 개념 스키마 = 통합 관점 = DB 전체 / 외부 스키마 = 사용자 관점
- 외부↔개념 = **논리적 독립성**, 개념↔내부 = **물리적 독립성**
